# TransPeek — Windows Packaging, Signing, Store, Update & Quick TTS: Direction Report

**App in scope:** TransPeek — free open-source English-learning translation app, WinUI 3 + C# + .NET 8, Windows App SDK 1.8.12, currently unpackaged (`WindowsPackageType None`), self-contained win-x64, ~150 MB ZIP (bundled Tesseract language data) via GitHub pre-releases `v0.1.3.<run>`, manual update check via GitHub Releases API, unsigned, speaker button currently does nothing. Developer: individual in Vietnam, zero-cost preference, GitHub-first.
**Research date:** 15–16 Nov 2026. Prices/fees are as published on the cited pages on those dates; re-check at checkout/submission — several prices vary by vendor/channel (see §2).
**Headline:** Ship 0.1.4 on GitHub with **Velopack (Setup.exe + silent delta auto-update)**, stay unsigned-or-SignPath for that release, **apply to SignPath Foundation now (free) in parallel**, and **defer the Microsoft Store to the next release** (free account, but MSIX conversion + certification is a second workstream). Do the **system-voice TTS in hours** before 0.1.4; do **not** ship Edge online voices as the main TTS.

**Two TransPeek-specific notes.**
- **150 MB matters:** with ZIP/Inno/MSI every update re-downloads all 150 MB. Velopack deltas and MSIX block-maps both avoid re-downloading unchanged Tesseract files; Velopack gives you that without the Store/signing prerequisites.
- **Windows App SDK 1.8.12 is out of servicing** (end of servicing 24 Sep 2026; current stable is 2.5.1, Sep 2026). It does not block Velopack or 0.1.4, but plan the 1.8 → 2.x upgrade soon — do not let the first packaged/Store attempt be on an unsupported SDK.

**Recommendation (§1): Velopack first.** It is the only option that solves installer *and* auto-update in one free, GitHub-native step, with no signing prerequisite. Keep publishing the ZIP alongside it as a portable fallback. If Velopack slips, Inno Setup is the fallback installer — not WiX, not Squirrel.

## 2. Code Signing (Windows)

### What the user sees when unsigned / self-signed

- **Unsigned (today):** "Windows protected your PC — Microsoft Defender SmartScreen prevented an unrecognized app from starting", Publisher: **Unknown publisher**, hidden "More info → Run anyway". On new Windows 11 installs Smart App Control may **block unsigned code outright** (no Run-anyway path). Microsoft's own table gives a **self-signed certificate the same behaviour as no signature** for public users — it only helps if the user manually installs your cert as a trusted root (dev machine / managed enterprise). So the macOS-style self-signed route does **not** transfer to Windows distribution.
- **Signed with a trusted cert, but new:** still a SmartScreen warning on first downloads ("unrecognized app", but with your verified publisher name shown). Reputation is two signals — publisher/certificate reputation + per-file hash reputation — and builds over "several weeks and hundreds of clean installs" (Microsoft gives no exact threshold; secondary reports cite ~15,000 downloads in 2026, unverified). Crucially, **signed builds inherit certificate reputation across versions; unsigned builds start at zero on every release.** Always timestamp (RFC 3161) so the signature survives certificate expiry.
- **Store apps:** no warning at all — Microsoft re-signs and the app carries full reputation (§3).

### How signing works in GitHub Actions CI

- **Paid OV/EV (modern, post-2023):** do **not** store a PFX in a secret — new publicly-trusted certs cannot be exported as a PFX (HSM mandate). Use the CA's cloud signing (e.g. SSL.com eSigner/CodeSignTool, DigiCert KeyLocker/smctl) or Azure Artifact Signing's action with OIDC/Azure login; secrets hold API credentials/tokens, never the private key. Sign with `signtool` (Windows SDK, preinstalled on `windows-latest` runners) + RFC 3161 timestamp, e.g. `http://timestamp.digicert.com` or `http://timestamp.acs.microsoft.com`, `/fd SHA256 /tr … /td SHA256`, then `signtool verify /pa`.
- **SignPath (free):** no private key in GitHub at all. CI builds the artifact in a GitHub-hosted job, uploads it as a workflow artifact, then `signpath/github-action-submit-signing-request@v2` submits it with `SIGNPATH_API_TOKEN` (secret, from a dedicated least-privilege CI user) + organisation/project/signing-policy slugs (non-secret variables). A human approver approves in the SignPath portal; the action waits, downloads the signed artifact, and only that signed output is published to the release. Pin the action to a commit SHA, sign only on tag pushes, never on PRs.
- **Self-signed (dev only):** the old base64-PFX-as-secret pattern still works for a self-signed test cert, and only for that. Do not copy it for a production cert.

**Recommendation (§2): Apply to SignPath Foundation now, in parallel with the Velopack work; ship 0.1.4 with Velopack unsigned if SignPath has not approved yet (with a clear SmartScreen note in the release notes: "More info → Run anyway", publisher will show Unknown until signing lands). Do not buy OV yet; do not buy EV at all; Azure is unavailable to a Vietnam individual. If SignPath declines, buy the cheapest reputable reseller OV (SSL.com/Sectigo via reseller, ~$129–220/yr band) before the Store launch, and keep the same cert/identity for every release so reputation accumulates.**

## 3. Microsoft Store

### What it takes

- **Account — now free for individuals.** Microsoft waived the old $19 individual fee (June/September 2025 rollout, "nearly 200 markets"). Entry point matters: start only at **storedeveloper.microsoft.com** → "Get started for free" → Individual developer; other paths (direct Partner Center / Xbox / Visual Studio) show the legacy paid flow. Company accounts were $99 one-time; Microsoft removed that fee in May 2026 per secondary reports (not needed here — individual is the right type, and an individual account cannot later be converted to a company account).
- **Identity verification:** government-issued ID + selfie (mobile capture), Microsoft account, MFA. No payment, no credit card in the new flow. Verification time is not published by Microsoft for individuals (company manual review is 2–5 business days); allow a few days.
- **Packaging — MSIX is the path, with one alternative.** WinUI 3 is packaged as MSIX by default; TransPeek deliberately opted out (`WindowsPackageType None`), so to submit as MSIX it must opt back in (remove that property / enable MSIX tooling, or add a packaging project). An unpackaged app **cannot** be submitted as MSIX (no package identity). Alternative: submit the existing **MSI/EXE installer** through the Store's Win32 path — but then Microsoft does **not** re-sign it, the installer must already be signed with a Trusted-Root CA cert (self-signed rejected), and that route does not solve signing. For TransPeek, MSIX is the point of going to the Store.
- **No signing cost via MSIX:** Microsoft re-signs the package after certification — no certificate to buy, manage or renew, and Store apps never see a SmartScreen download warning. This is the Store's biggest financial advantage for a $0 project.
- **Submission contents:** reserve the app name in Partner Center (reservation lasts 3 months until first submission), upload `.msixupload`/`.msixbundle`, category, age rating (IARC questionnaire), description, at least one screenshot, privacy policy URL if applicable, pricing (free). **Capabilities:** a Win32/WinUI app will typically declare the restricted `runFullTrust` capability — that triggers a manual review step and you must justify it in the submission; allow extra time.
- **Certification / policy checks relevant to TransPeek:** certification takes **up to 3 business days** (Microsoft's published figure; indie reports typically 1–3 business days, first submissions slower, listing visible ~15 min after passing). Tests: security/malware scan, technical compliance, content compliance against Store Policies v7.20 (eff. 22 Oct 2026). For a translation + OCR app the live checks are generic, not category-specific: **10.1** distinct function/value + accurate representation (describe what it does, no misleading screenshots); **10.2** security — no malware, no bundled non-integrated third-party software, no downloading/executing remote code beyond the described function; **10.2.5** all Store products must be installed/updated **only through the Store** — so a Store build must **not** run Velopack self-update (detect packaged vs unpackaged at runtime and disable the Velopack path in the Store build; a dual-track build from one codebase is a proven pattern). Also: bundled Tesseract language data is fine (fully contained in the package), and any online translation API use must be disclosed accurately; user-generated/translated content has no special policy, but the listing must not promise a translation service you do not operate. No age-rating or health/finance-style extended review is expected.
- **Revenue:** free app → no Store fee. (For reference: 15% on apps / 12% on games if using Microsoft commerce; 0% if using your own commerce for a non-game app — irrelevant while free.)
- **Sideloading / GitHub alternative:** sideloading an MSIX outside the Store is always possible (double-click / App Installer, sideload enabled by default since Windows 10 2004), but the MSIX must be signed with a trusted cert — i.e. it re-introduces §2. GitHub + Velopack remains the zero-friction channel: no review, no listing work, instant publish, but no Store discovery and no SmartScreen exemption.

**Recommendation (§3): Defer the Store to the release after 0.1.4 — but start the free account registration now** (it costs nothing and the ID check is the long pole). Sequence: 0.1.4 = Velopack on GitHub → 0.1.5 (or a 0.1.4.x Store build) = MSIX + Store submission, with the Velopack updater disabled in the packaged build. The Store is worth it for a free OSS app precisely because it is now free and is the only route that removes SmartScreen warnings entirely without buying a certificate — it is a distribution/trust upgrade, not a revenue play, and it should not gate the first real release.

Sources: https://learn.microsoft.com/en-us/windows/apps/publish/whats-new-individual-developer, https://learn.microsoft.com/en-us/windows/apps/publish/partner-center/account-types-locations-and-fees, https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/publish-first-app, https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msi/app-certification-process, https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options, https://learn.microsoft.com/mt-mt/windows/apps/publish/store-policies; dual-track pattern https://github.com/fettah010/winui-3-easy-template/blob/HEAD/Templates/Project/docs/feature-guides/distribution-dual.md.

## 4. Update Notification / Delivery

### How the options compare

| Approach | How it works | User experience | Cost / effort |
|---|---|---|---|
| **Current: GitHub Releases API check** | Settings button → `GET api.github.com/repos/<owner>/<repo>/releases/latest` → compare tag → open the releases page in a browser. | Manual, only when the user thinks to press it; user must download ~150 MB, unzip, replace files, re-create shortcuts. No progress, no resume, no delta, no reminder. It is a notifier, not an updater. | Already built; ~0 extra work. |
| **Velopack (recommended)** | App (on launch + a timer, e.g. every 24 h while running) calls `UpdateManager(new GithubSource(repoUrl, null, false)).CheckForUpdatesAsync()`. That reads the `releases.{channel}.json` feed Velopack published to the GitHub release — **not** the GitHub API and not a version-string scrape. If an update exists: `DownloadUpdatesAsync()` fetches the delta `.nupkg` (only changed files) in the background, verifies checksums, stages it; `ApplyUpdatesAndRestart()` (or auto-apply on next startup, the default) swaps the install directory atomically and restarts. First Velopack release has no delta (full package only) — expected. `vpk upload github` generates the delta against the previous release automatically. | **Silent by default:** no prompt, update applies on next launch/restart. You choose the UX: fully silent; a small "Update downloaded — restart to apply" affordance; or a prompted "Update available — Download / Later". Silent + apply-on-restart is the least annoying and the norm for this class of app. A failed/partial download is discarded, the current install is untouched. | ½–1 day as part of §1 (same work — Velopack *is* the updater). No server, no feed hosting cost; the feed lives on GitHub Releases. |
| **MSIX / Store** | Store (or App Installer feed) checks and downloads updates automatically; differential via package block-map. | Silent, Windows-owned. User does nothing. | Comes with §3; not available to the GitHub channel. |
| **Hand-rolled (NetSparkle, etc.)** | Appcast/feed + full-installer download + relaunch. NetSparkle is the maintained C# Sparkle-style option, no delta updates (full download each time). | Prompted download + install, usually with a UAC/elevation step. | More code and more UX to design than Velopack, for a worse result on a 150 MB app. Only if Velopack is rejected for some reason. |

### Minimum viable update story for the first release

1. **If Velopack lands in 0.1.4 (plan A):** silent background check on launch (and at most once every 24 h), silent delta download, apply on next launch; show a one-line, dismissible in-app note in Settings ("Updated to 0.1.5 on next restart" / "You're on the latest version") and a non-blocking "Restart to update" button — never a modal dialog on launch, never a forced restart, never a download without the user having launched the app. That is the whole story; it needs no tray icon and no toast.
2. **If Velopack slips (plan B):** keep the current API check but fix its three worst gaps in an afternoon — check automatically once at startup (throttled to once a day, stored last-check date), show the result as a **dismissible in-app banner** (not a popup) with "Download" (opens releases page) and "Remind me later", and show the installed version + "Check for updates" in Settings. Do not auto-download a ZIP you cannot safely apply.

### Notifying without being annoying

- **In-app banner (best for unpackaged):** a slim, non-modal bar under the toolbar on the main/translation view, only when an update is actually available, with Download / Dismiss; remember the dismissal per version (do not re-show the same version every launch). This works with no package identity.
- **Settings row:** persistent "Version X · Check for updates · You're up to date" — the discoverable, non-intrusive home for the feature.
- **Toast / tray notification:** **not available for free to an unpackaged app** — Windows app notifications require package identity (packaged MSIX or sparse package). Do not build a custom tray-balloon workaround; wait for the MSIX/Store build, where notifications are a platform feature. A custom in-app toast-like panel is fine, a fake system toast is not needed.

**Recommendation (§4): Velopack silent update as the mechanism; in-app banner + Settings row as the notification. No toast until the Store/MSIX build. For 0.1.4, "check on launch, silent delta download, apply on restart, dismissible banner" is the target; the current manual API check is an acceptable fallback for one release only, with the once-a-day banner improvement.**

Sources: https://docs.velopack.io/integrating/overview, https://docs.velopack.io/getting-started/csharp; packaging/identity limits https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/packaging/; Store update rule (10.2.5) https://learn.microsoft.com/mt-mt/windows/apps/publish/store-policies.

## 5. Quick TTS via Edge (fast path before release)

### The two things people mean by "Edge TTS"

| | **Windows.Media.SpeechSynthesis (system voices) — the quick win** | **Edge Read Aloud online voices (edge-tts)** |
|---|---|---|
| What it is | Built-in WinRT API, part of Windows. `new SpeechSynthesizer()`, pick a voice from `SpeechSynthesizer.AllVoices`, `SynthesizeTextToStreamAsync(text)` → `SpeechSynthesisStream` → play with `MediaPlayer` / `MediaPlayerElement`. No key, no account, no NuGet, works offline. Documented Microsoft API. | The voices behind Edge's Read Aloud (Ctrl+Shift+U): Azure neural voices served from Microsoft's `speech.platform.bing.com` WebSocket. There is **no documented public API** for a desktop app to call them. The community `edge-tts` project (Python, rany2/edge-tts) reverse-engineered the browser's traffic (public token + `Sec-MS-GEC` header) and replays it. A C# port exists: **EdgeTTS.DotNet 0.4.0** on NuGet (MIT, targets net9.0/net10.0 — no net8.0 target listed, so verify .NET 8 compatibility before adopting). |
| Needs Edge installed? | No. | No — edge-tts does not need Edge installed; it talks to the service directly. That is also why it is fragile. |
| Needs internet? | No (once the voice/language pack is installed). | Yes, every utterance. Text is sent to Microsoft's servers. |
| Voice quality / languages | Robotic/older OneCore voices. en-US: David, Mark, Zira (installed by default on en-US Windows; on a Vietnamese-locale machine the en-US voices may be absent until the English language pack's Text-to-Speech feature is installed). Vietnamese: **An (male only)** in Microsoft's published list; a natural-voice set (Guy/Jenny/Aria en-US, etc.) exists for Narrator but is not generally exposed through `SpeechSynthesizer`. Acceptable for hearing a word/sentence pronounced; clearly worse than neural voices. | Neural, natural — the best free voices most users can access. 300+ voices, 70+ locales, including high-quality en-US (Aria, Jenny, Guy) and Vietnamese neural voices. This is the quality gap that makes Edge tempting. |
| Reliability / ToS | Fully supported, will not break. | **Unofficial, no SLA, can break without notice — and has:** Microsoft changed the token check in Oct 2026 and edge-tts ≤7.2.x started failing with HTTP 403; ≥7.3.1 fixed it. Microsoft's Q&A position (reported in community research) is that using the service outside Edge without an Azure subscription is not a licensed use. Treat it as a hobby fallback, not a shipped feature of a public app. |
| Effort in WinUI 3 | **2–4 hours for a working speaker button** (synthesise → play, stop on second click, disable with a tooltip when no voice for that language is installed); **~½ day polished** (voice pick per language — en vs vi — rate control, queue/cancel, error handling, Settings voice choice). No new dependency, no secret, no network permission to explain. | **½–1 day** to wire EdgeTTS.DotNet (or a small WebSocket client) + MP3 playback + fallback, **plus ongoing maintenance risk** every time Microsoft rotates the token. And it still needs the system-voice fallback for offline/no-network users, so it is additive work, not a replacement. |
| The official neural alternative | — | **Azure AI Speech (official):** same neural voices, documented SDK. Free tier F0 = **500,000 neural characters/month, never expires** (20 req/min), then ~$15–16 per 1M characters (Neural HD $22). But it needs an Azure account + key/region, and a **shared key must not be embedded in an open-source client** — each user would need their own key, or you would need your own proxy server (cost + abuse risk). Not a drop-in for a free OSS app. |

### Plain answer

**Edge online voices are not practically usable as the shipped TTS for TransPeek.** There is no documented API, no Edge-install requirement to lean on, and the only route is a reverse-engineered WebSocket that Microsoft has already broken once in Oct 2026 and may throttle or change again. It is fine as an experiment; it is not a dependency to put in front of learners in a first stable release.

**Recommendation (§5): Ship the speaker button on `Windows.Media.SpeechSynthesis` before 0.1.4 — it is a genuine quick win (hours, offline, no key, no new dependency). Pick the voice by the text's language (en → en-US voice, vi → vi-VN "An" if installed), fall back to the system default voice, and disable the button gracefully with an explanatory tooltip when no voice for that language exists (point the user at Settings → Language → Text-to-Speech). Keep Edge/Azure neural voices as a later, opt-in enhancement — Edge as an explicitly-labelled experimental fallback, or Azure with a bring-your-own-key field — not as the default.**

## Could not verify / open questions

- **SignPath current intake status:** secondary sources conflict (one says applications temporarily paused for backlog; another reports a rejection for low visibility). The official pages confirm the programme exists and is free, but **check https://about.signpath.io/product/open-source and https://signpath.org/apply at apply time** — approval is a human decision and is not guaranteed for a young project with few releases.
- **Azure Artifact Signing country expansion:** Microsoft Learn (opened 15 Nov 2026) lists orgs USA/Canada/EU/UK, individuals USA/Canada. A Nov 2026 secondary source claims 12 org countries. The disagreement does not change the conclusion (Vietnam individual excluded either way), but do not rely on the expanded list without re-checking Microsoft's own quickstart.
- **OV/EV prices:** Microsoft Learn's bands ($150–300 OV, $400+ EV) conflict with vendor-direct prices (DigiCert $696 OV / $972 EV) and reseller prices (SSL.com $129 OV, Sectigo $219 OV). The gap is channel/multi-year/token — treat all figures as "re-check at checkout" bands, not quotes.
- **SmartScreen download thresholds:** Microsoft publishes no number; "several weeks / hundreds of installs" is its own wording, higher figures in secondary sources are unverified.
- **Store individual verification time:** Microsoft publishes no SLA for the ID check; allow a few days.
- **EdgeTTS.DotNet on .NET 8:** the NuGet page lists net9.0/net10.0 targets only; .NET 8 compatibility was not verified, and TransPeek is on .NET 8 — confirm before any Edge experiment.
- **Whether TransPeek's licence is OSI-approved** (a SignPath hard requirement) and whether the repo already has a qualifying prior release in the exact form to be signed — not verified from the mission text; confirm before applying.
